> [!summary] 핵심 한 줄
> 쿠버네티스는 **파드**(컨테이너 묶음)를 **컨트롤러**(디플로이먼트→레플리카셋)로 자동 관리하고, **서비스**로 네트워크를 추상화한다. 키워드는 **셀프힐링·오토스케일·무중단 배포**.

---

## 1. 파드 (Pod)

쿠버네티스의 최소 배포 단위. 1개 이상의 컨테이너를 묶고, **네트워크(같은 IP)·볼륨을 공유**한다.

### 사이드카 패턴 (Sidecar)

- 한 파드에 **메인 컨테이너 + 보조 컨테이너**(로그 수집기, 프록시 등)를 함께 배치
- **볼륨 공유**로 메인이 쓴 로그를 사이드카가 읽어 수집·외부 전송
- 메인 컨테이너 코드를 건드리지 않고 **부가 기능(로깅·모니터링·통신)을 분리**하는 게 목적

> [!example] 대표 사례
> 메인 앱 + 로그 컨테이너(Fluentd 등) → 공유 볼륨의 로그를 사이드카가 외부로 전송. 서비스 메시(Envoy 프록시 주입)도 같은 패턴.

---

## 2. 워크로드 컨트롤러

### 디플로이먼트 (Deployment)

- **파드 셀프힐링** 가능: 파드가 죽으면 자동 재생성
- 정확한 구조: **디플로이먼트 → 레플리카셋 → 파드**
  - **레플리카셋(ReplicaSet)**: 지정한 개수의 파드를 유지·관리 (실제로 파드를 직접 감시)
  - **디플로이먼트**: 레플리카셋을 관리하며 **배포(rollout)·롤백** 담당
- 즉, 셀프힐링은 레플리카셋이, 버전 관리는 디플로이먼트가 한다.

```
Deployment ──관리──▶ ReplicaSet ──관리──▶ Pod, Pod, Pod
   (배포/롤백)          (개수 유지/셀프힐링)
```

### 롤링 업데이트 (Rolling Update)

- 새 버전 파드를 **하나씩 만들면서 기존 파드를 하나씩 제거**하는 과정을 반복
- 서비스 중단 없이 점진 교체 → **무중단 배포**
- 문제 발생 시 디플로이먼트로 **롤백** 가능

### HPA (Horizontal Pod Autoscaling)

- **부하량(CPU·메모리·커스텀 지표)에 따라 파드 개수를 자동 조절**
- 수평 확장(파드 수 늘리기) — 트래픽 급증 시 자동 스케일아웃, 한산하면 스케일인
- (cf. 수직 확장 VPA는 파드 자원 자체를 키움 — HPA와 구분)

## 3. 서비스 (Service)

파드는 죽고 살아나며 IP가 계속 바뀐다. 서비스는 **고정 진입점(고정 IP/DNS) + 부하분산**을 제공해 클라이언트가 파드에 쉽게 접근하게 한다.

| 타입 | 접근 범위 | 용도 | 우리 케이스 |
|---|---|---|---|
| **ClusterIP** | 클러스터 **내부** 파드 간 통신만 | 내부 서비스 연결 (기본값) | risk·merchant-limit·order·redis·kafka-bootstrap — 파드끼리 DNS로 호출 |
| **NodePort** | 내부 + **외부에서 노드IP:포트** 접근 (30000~32767) | 테스트·개발, 클러스터 밖 클라이언트 | `merchant-limit-np:31574` — 클러스터 밖 k6 시드가 merchant 생성용으로 직접 호출 |
| **LoadBalancer** | 외부 LB를 통해 노출 | 클라우드 환경 외부 노출 | k3s 내장 **klipper-lb(svclb)**가 역할 담당 → Traefik이 이 타입으로 노드:80/443 개방 |
| **ExternalName** | DNS CNAME 리다이렉트 | 클러스터 외부 서비스에 내부 DNS명 부여 | 미사용 |

### Ingress — L7 라우팅 규칙

서비스가 L4(IP:Port) 분산이라면, **인그레스는 L7(경로·호스트 기반)** 라우팅 규칙이다. 서비스 타입이 아니라 별도 오브젝트.

- **인그레스 컨트롤러**가 규칙을 실행함 — k3s 내장은 **Traefik**.
- 우리: 경로 `/` → payment Service. Traefik이 LoadBalancer 타입 서비스로 노드에 바인딩.

> [!tip] 외부 노출 전략
> NodePort/LoadBalancer는 L4, **인그레스는 L7**. 도메인·경로 기반 분기·TLS 종료까지 한 곳에서 처리하려면 인그레스를 쓴다.

## 4. 컨트롤 플레인 / 노드 컴포넌트

쿠버네티스(k3s 포함)는 **컨트롤 플레인(마스터)**과 **워커 노드**로 나뉜다.

### 컨트롤 플레인

| 컴포넌트 | 역할 | 우리 케이스 |
|---|---|---|
| **kube-apiserver** (:6443) | 모든 요청의 정문 (kubectl·kubelet·컨트롤러 전부 여기로) | agent join, kubectl 명령 전부 apiserver 경유 |
| **kube-scheduler** | 파드를 어느 노드에 배치할지 결정 (nodeSelector·taint/toleration·anti-affinity 반영) | payment를 전용 노드풀에 배치한 주체 |
| **controller-manager** | 제어 루프 집합체 (Deployment→ReplicaSet→Pod 관리, 롤아웃 조정) | 레플리카셋 개수 유지, 롤링업데이트 실행 |
| **datastore** | 클러스터 상태 저장. **k3s 기본은 SQLite** (단일 서버, etcd 아님) | 단일 서버 구성; HA 전환 시 etcd/외부 DB 필요 |

### 워커 노드 (전 노드에 존재)

| 컴포넌트 | 역할 | 우리 케이스 |
|---|---|---|
| **kubelet** | apiserver와 통신, containerd로 컨테이너 실행·상태 보고 | 각 노드에서 파드 실행·헬스 보고 |
| **kube-proxy** | iptables/ipvs 프로그래밍 → ClusterIP·NodePort **L4 분산** | payment Service → 3파드 분산이 이것 |
| **flannel** (CNI) | 파드망 `10.42.0.0/16`, 노드 간 파드 트래픽 VXLAN 캡슐화 | 멀티 노드 간 파드 직통 통신 |
| **CoreDNS** | 서비스명 → ClusterIP DNS 해석 | `payment-svc` 같은 이름 → IP 변환 |
| **Traefik + klipper-lb** | k3s 내장 Ingress 컨트롤러 + 서비스 LB (노드:80/443) | 외부 트래픽 수신 → payment Service 전달 |

## 5. 한눈에 정리

- **파드**: 컨테이너 묶음, 네트워크·볼륨 공유 → 사이드카로 부가기능 분리
- **레플리카셋**: 파드 개수 유지(셀프힐링)
- **디플로이먼트**: 레플리카셋 관리 + 롤링업데이트/롤백
- **HPA**: 부하 기반 파드 수 자동조절
- **서비스**: 고정 IP + 부하분산 (ClusterIP=내부, NodePort=외부직접:30000~32767, LoadBalancer=LB위임, Ingress=L7 경로기반)
- **컨트롤 플레인**: apiserver(정문:6443)·scheduler(배치결정)·controller-manager(제어루프)·datastore(k3s=SQLite)
- **노드**: kubelet(실행·보고)·kube-proxy(L4분산)·flannel(CNI 10.42.0.0/16)·CoreDNS(이름해석)

## 6. Strimzi — Kafka 오퍼레이터

### Kubernetes Operator 패턴

- **CRD(Custom Resource Definition)** 로 상태를 **선언**하면, 오퍼레이터가 실체(파드·서비스·스토리지)로 **reconcile**한다.
- StatefulSet을 손으로 관리하는 대신 원하는 상태를 YAML로 선언하고, 오퍼레이터가 현재 상태와 차이를 지속 조정.

### 우리 케이스

| CRD | 역할 |
|---|---|
| `Kafka` | 클러스터 전체 선언 (KRaft 모드, 3-broker, RF3 / minISR2) |
| `KafkaNodePool` | 브로커·컨트롤러 노드 풀 분리 선언 |
| `KafkaTopic` | 토픽별 파티션·RF 선언 (4토픽) |

- 3-broker 클러스터를 Strimzi로 선언 배포 — ZooKeeper 없이 KRaft, RF3/minISR2 설정.

> [!tip] Operator 패턴 핵심
> "어떻게 만들지"가 아니라 **"무엇이 있어야 하는지"** 를 선언. 오퍼레이터가 나머지를 책임진다.
